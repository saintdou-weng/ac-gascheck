# 2026-10-06 發送修正與更新方式

本版以這次提供的 ac-gascheck-main(5).zip 與 gascheck.txt 為基礎。原有精簡 Telegram 卡片、日週月年選擇、照片、AM/PM、四區資料、刪除保護、各項核可、Phea 審查人與 Paul 核可人欄位均保留。沒有清除或重建正式資料。

## 截圖與已修正問題

截圖選的是 Recycle，預覽有 2,515 kg，按 Send 後停在 Syncing，尚未到 Telegram 發送。截圖沒有後端錯誤紀錄，不能僅憑畫面判定正式站當次卡住的唯一原因；原始程式確實有以下可重現的缺陷，這次已處理：

- EHS 同步前等待舊刪除 API；即使失敗會被 catch，仍須先等整個請求結束。改用既有刪除墓碑隨同步提交，下載仍保留本機刪除保護。
- 共用同步允許上傳、下載同時執行。現在同一頁同一模組依序執行；發送前如果等的是較早開始的背景上傳，會再上傳最新資料快照。
- 雲端逾時保護在收到回應標頭後就結束；若回應內容未下載完，會永久等待。現在 GET/POST 的完整回應內容都受逾時保護。寫入仍保留長等候與退避，避免伺服器尚在寫入就大量重送。
- Send 只顯示 Syncing，無法知道正在做什麼。改為檢查雲端、照片上傳數量、資料上傳、確認儲存、發送 Telegram 各階段提示。
- Recycle/Waste 等單頁報告重試時可能新增同樣訊息。現在同一模組、期間、資料範圍、時段、語言會沿用原報告卡；既有 AM+PM 同日更新規則優先保留。照片依送達紀錄去重，文字送達但照片失敗不會顯示全部成功。
- GS 原本對任何 Telegram 錯誤都再發一次去格式文字，連網路錯誤、限流、群組權限錯誤也重送。現在只有確認為 HTML 格式錯誤才走去格式備援，其他錯誤直接回報。
- Cleaning、Dormitory、EHS、Portal 的原生 API 發送入口也採用相同完整回應逾時保護；舊快捷發送保留連按保護並在上雲後重建摘要。

發送前仍須確認資料已上雲。歷史資料未上傳成功會明確報錯，不會跳過儲存而假裝發送成功；歷史照片失敗只阻擋包含該照片記錄的摘要。

## 宿舍摘要與照片修正

- 原宿舍摘要只收人員申請作為「可發送資料」判斷，巡查照片也只取異常房間。現在摘要資料源納入巡查／違規，和人員申請的雲端資料仍分開保存；只有巡查的日期也能發送。
- 發送部份可單獨選：人員入住／離開、只入住、只離開、全部設施檢查、宿舍檢查、外籍宿舍檢查、當地宿舍檢查、工廠檢查、辦公室檢查、違規；既有按房間發送的選項保留。選取的期間及部份同時限制預覽、照片與可發送資料。
- 每個房間顯示最新檢查結果：✅ 全部通過，❌ 有異常時列出項目，❌ 未完成／未檢查則明確說明。未檢查不會假算成通過。檢查人與日期保留；同房間重複巡查取期間內最新狀態，另列次數。
- 巡查原生「發送」在有填寫內容時先儲存；已按儲存清空輸入時，改讀同日期／地點的已存巡查，不會漏掉已存照片。先確認巡查資料及照片上雲，再發摘要，照片上傳失敗會停下並可重試。
- 宿舍、溫度、清潔、回收／廢料、鑰匙及水桶：選取記錄的正常及異常照片都附上；資產修正了摘要照片變數遮住資產照片表，並附上所選資產的照片。
- 不再只取前 5 張；每次雲端發送請求最多 5 張，後續只續傳照片，不重發摘要文字。全部照片確認送達後才記錄本次報告完成。文字或前批照片已送達時，重試沿用原卡並略過已送照片。大型月年報的照片送達紀錄另存雲端，保留完整去重紀錄。
- 宿舍只發入住／離開摘要時，後端只標記對應人員申請已發摘要；只發巡查不會把尚未發送的人員申請當成已發。Phea 審查人、Paul 核可人，以及原本逐筆 Telegram 核可／退件卡仍保留。

## GS 更新及執行

1. 在原本 AC_GASCHECK_CORE 專案，以本包 `ac_gascheck_core_v3_fixed.gs` 的完整內容更新原 GS 主檔；也可使用隨附 `gascheck-v63.txt`，兩者內容相同。不要把兩份同時貼入同一專案。原上傳檔的 CFG 連線與核可人設定已原樣保留。
2. 按儲存，再進入「部署 → 管理部署」，編輯網站目前使用的原 Web App 部署，版本選「新版本」，部署。請沿用原 `/exec` 網址，勿改建另一個網址。
3. 在函式下拉選單選 **`檢查發送連線`**，按「執行」一次，首次要求授權時完成授權。這個函式只檢查 Bot、群組、文字／照片權限與核可接收狀態，不會發測試訊息、改 webhook、清資料或新建排程。
4. 查看執行記錄：`fixVersion` 應為 **`v5.2-delivery-sync-1006`**；`checks` 各項 `ok:true` 才表示對應檢查通過。`ok:false` 時保留該項 `name`、`detail` 回報，能區分 Bot token、群組權限與核可接收問題。此檢查是在編輯器的新程式執行，仍須完成第 2 步才能讓網站使用新程式。

這次不需執行 init、upgradeGascheckV53、資料清理、重置 UID 或更換核可接收方式。既有排程沿用；不要為處理 Send 卡住重複新增 trigger。

## 更新後操作確認

- 在 EHS 選有記錄的日期，分別選 Recycle 與 Waste，確認進度提示最終顯示送達，群組內容與預覽一致。
- 同一報告重試應更新原卡；期間或資料範圍不同會是各自的報告。若提示照片失敗，完成重試後才視為整份送達。
- 刪除一筆測試資料、上傳後再下載，應維持刪除；新增或編輯後同樣確認下載內容為最新版本。
- 若仍失敗，提供 Send 下方完整錯誤、`檢查發送連線` 中失敗項目，以及 Apps Script 對應時間的執行錯誤。請不要提供 Bot token。

- 宿舍選「宿舍檢查」及有巡查的日期，預覽應包含逐間結果及照片數；沒有入住申請也可送。切成「人員入住／離開」或「工廠檢查」，內容及照片應只剩該部份。
- 在巡查頁填寫、附照片、先按儲存，再按發送，確認日期／地點的已存照片都有送出。選擇「宿舍檢查」摘要不會替人員申請完成核可。
- 多於 5 張照片會分批送出；失敗時顯示錯誤，重試只補失敗照片並更新同一摘要卡。
